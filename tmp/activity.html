💻 A IA responde bem em uma conversa e diferente na conversa seguinte. O pedido era o mesmo. O que faltava não era um prompt mais longo.

🎯 Skills e rules são o que fazem a IA repetir um método, em vez de improvisar um a cada chat.

Uma skill é o procedimento de um trabalho: quando usar, os passos, o que entregar e o que fica de fora. Uma rule é a restrição que vale o tempo todo, mesmo quando você não citou skill nenhuma. Juntas, elas tiram o melhor do modelo porque o critério deixa de morar só na sua cabeça.

🚀 Publiquei o public-skills, um pacote aberto com seis skills dentre algumas que eu uso de verdade no dia-a-dia. Licença MIT.

Nos próximos posts eu entro em cada uma:
→ ✏️ logo — marcas em SVG, com estratégia antes de desenhar
→ 🎨 branding — guia de marca; pede a skill logo junto
→ 🖥️ frontend-design — interface com cara de produto, não de template
→ 📋 daily-standup — texto de daily no formato do time
→ 🔀 cherry-pick-env-prs — levar uma PR já mergeada para outras branches
→ 🔍 pr-review — review em arquivo local, sem aprovar nada no GitHub por você

      📍 No post anterior comentei o scraper que montei para coletar publicações do LinkedIn. Hoje o foco é o que veio depois: como esse fluxo entra no ar, sem expor credencial e sem rodar coleta quando alguém abre o site.

      💻 O problema era simples — queria mostrar conteúdo recente no portfólio, mas RSS, embed e API oficial não fecharam o ciclo com qualidade. Já tinha tentado isso antes e tirei do escopo. Desta vez separei coleta e exibição de propósito.

      🚀 Como ficou na prática:
      → O scraper roda localmente, no repo linkedin-posts
      → Ele grava texto, mídia, reações e data no Supabase (cache próprio)
      → O portfólio só consulta GET /api/linkedin-posts — Function na Vercel, com service role apenas no servidor
      → Visitante nunca dispara scraping — só lê cache já pronto

      📚 Na seção do portfólio:
      → Três publicações mais recentes em feed vertical, no estilo LinkedIn
      → Texto formatado, links clicáveis e hashtags separadas do corpo
      → Imagens e vídeo via proxy server-side (o CDN do LinkedIn não hotlinka direto no browser)
      → Botão “Ver mais posts” leva para a atividade no perfil

      💡 O scraper virou infra de atualização; o portfólio virou vitrine. Atualizo o cache no meu ambiente, quando faço push dos dados. Quem navega só consome o que já está persistido — previsível, rápido e alinhado ao que já uso (React, TypeScript, Vite, Supabase, Vercel).

      🎯 Se você também quer portfólio que reflete o que publica fora do GitHub, vale separar coleta de exibição. Menos acoplamento, menos surpresa em produção.

      👉 Veja a seção no ar:
      🔗 https://lnkd.in/dM22VvVC

        💻 Queria uma seção de posts recentes no meu site — sem copiar texto manualmente toda vez que publicava no LinkedIn.

        🔍 Antes de qualquer scraper, fui pelas APIs já existentes e verificadas do LinkedIn. Para posts de um perfil pessoal — o meu caso — encontrei muita fricção: permissões restritas, escopos que não cobrem o que eu precisava, produtos voltados a páginas e campanhas, não a exibir o feed público de uma pessoa no portfólio.

        🚀 Depois de esgotar o caminho oficial, montei algo simples, sob meu controle e sem depender de deploy na nuvem.

        📍 Lancei o linkedin-posts: coleta os posts públicos de um perfil no seu PC via scraping local, grava o cache no Supabase e deixa qualquer site (portfólio, blog, landing) consumir esses dados por Function ou API route.

        Como funciona:
        → Login manual no LinkedIn via Playwright (2FA incluso — sem gambiarra de bypass)
        → `yarn scrape` persiste os posts no PostgreSQL do Supabase
        → Seu site lê o cache no servidor — credenciais sensíveis ficam fora do browser
        → No Windows, dá para agendar coleta no logon (sessão válida = silencioso; expirada = abre o login de novo)

        Stack: Node.js 22, TypeScript, Playwright, Supabase, Fastify (API local opcional).

        💡 É open source (MIT). Não substitui a API oficial — é um caminho pragmático para quem, como eu, não conseguiu resolver isso só com o que o LinkedIn expõe hoje.

        👉 Repo, README e guias de setup:
        🔗 https://lnkd.in/duWCgzwq

        💻 Quem roda API Node em PaaS no plano gratuito conhece o cenário: ~15 minutos sem tráfego e a instância hiberna. Cold start na próxima requisição, latência alta e aquele log silencioso no painel.

        🚀 Lançamento: @rafaelhdsv/keep-alive

        Self-ping periódico para Web Services Node que dormem por inatividade (Render Free, Railway, Fly.io e similares). Depois do `app.listen`, o pacote faz GET na rota de health do próprio app, usando a URL pública configurada.

        → Zero dependências de runtime — `fetch` nativo do Node 18+
        → CLI `init` para Express: um comando e o projeto fica pronto
        → Uso manual em Fastify, Hono e outros frameworks
        → No-op silencioso em dev local (sem URL pública configurada)
        → MIT, open source, documentação completa no README

        💡 Não é SLA nem substituto de plano pago — é workaround prático para idle enquanto o processo Node está no ar. Para quem já tem o app rodando e quer evitar hibernação sem mais um serviço na pilha.

        💻 Na empresa em que trabalho, o time grava dezenas de vídeos de treinamento sobre o produto — e o cronograma vivia num texto enorme no canal interno.

        Percebi o atrito no dia a dia: atualizar horário, marcar o que já foi gravado ou adiar sessão virava caça ao trecho certo, e qualquer deslize afetava a coordenação de todo mundo.

        🚀 Em vez de conviver com isso, identifiquei o problema e busquei uma forma melhor: tirei o cronograma do “texto corrido” e coloquei num painel web, com uma URL para consultar e, para quem coordena, editar com controle.

        ✅ O que construí (Cronograma de Gravações):
        → Resumo com progresso global e por pessoa
        → Calendário mensal (sessões do dia, adiar, remarcar, trocar horário no mesmo dia)
        → Visão por gravador com checklist por tópico
        → Fila de alterações + modal “confirmar tudo” antes de persistir no banco (menos clique errado)
        → Leitura aberta na URL; edição só no modo editor (senha da equipe)

        📚 Stack na prática: React + Vite, API Node/Express, sessões no Supabase; catálogo versionado em YAML no repo.

        💡 O ganho que mais me importou não foi só “ter calendário bonito” — foi atacar um gargalo real do time, separar quem só consulta de quem altera, e tratar remarcação como dado estruturado, não como mais uma mensagem perdida no chat.

          💻 Superlotação, fila imprevisível, triagem no papel e histórico espalhado — esse cenário motivou o MedIT, nosso TCC em Análise e Desenvolvimento de Sistemas.

          🚀 O MedIT é uma plataforma web full stack para organizar o fluxo hospitalar e apoiar a triagem clínica. Não substitui profissionais de saúde e não faz diagnóstico automático: é apoio à decisão e gestão operacional.

          📚 O que o sistema faz na prática:
          → Paciente: pré-atendimento remoto (status "a caminho"), confirmação de chegada e acompanhamento da jornada no dashboard
          → Enfermagem: fila de triagem, sinais vitais editáveis, classificação de risco e encaminhamento para o médico
          → Médico: fila de consultas, histórico, sugestões por regras e conclusão do caso com diagnóstico e prescrições
          → Administrador: dashboard com entradas, em atendimento, atendidos e ocupação; gestão de usuários, medicamentos e unidades parceiras

          🎯 Diferencial técnico — IA simbólica, não generativa:
          → Base sintoma-doença com pesos curados no MongoDB
          → Compatibilidade em percentual, transparente e determinística
          → Quem decide é sempre o médico; o sistema só sugere possibilidades a partir dos sintomas informados

          ⚙️ Stack e arquitetura (monorepo):
          → Front-end: React 19, Vite 7, TypeScript, Ant Design, Sass, React Router
          → Back-end: Node.js, Express 5, TypeScript, Mongoose 9
          → Segurança: JWT access/refresh, bcrypt, isolamento por unidade e por titular do atendimento
          → Filas com claim atômico (enfermeiro/médico) para evitar dupla captura do mesmo caso

          💡 Também implementamos modo tela cheia no painel da fila (útil para sala de espera), tema claro/escuro, seeds de demonstração com volume realista e scripts de carga via yarn scripts.

          ⚠️ Escopo acadêmico: protótipo funcional com dados simulados, sem integração com sistemas oficiais do SUS.

          🔗 https://lnkd.in/deyjayhD

          Nessa terça-feira tive a oportunidade de apresentar meu Trabalho de Conclusão de Curso (TCC) e concluir minha graduação em Análise e Desenvolvimento de Sistemas com o desenvolvimento do MedIT, uma plataforma digital que, junto ao meu grupo, criamos para apoiar a triagem e a organização do fluxo hospitalar.
          O projeto foi desenvolvido com o objetivo de melhorar a experiência tanto dos pacientes quanto dos profissionais da área da saúde, além de otimizar os processos de atendimento em unidades de saúde e a gestão do fluxo de pacientes por meio de recursos como:

          • Cadastro digital de pacientes;
          • Pré-atendimento remoto;
          • Organização automática de filas;
          • Histórico clínico centralizado.

          No lado mais técnico, a solução foi desenvolvida utilizando React + Vite no front-end, Node.js, Express e TypeScript no back-end, além do MongoDB como banco de dados. Na parte de segurança, contamos com mecanismos alinhados à LGPD para garantir a proteção e a rastreabilidade das informações.
          Além disso, foi implementado um sistema de apoio à decisão baseado em regras (IA simbólica), capaz de fornecer sugestões de possíveis diagnósticos aos profissionais da área, sempre mantendo a decisão clínica sob responsabilidade do profissional de saúde.
